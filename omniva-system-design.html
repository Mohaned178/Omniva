Omniva System Design

System Design completed 24 Nov 2026 (D1–D9, ADRs 0001–0019). Development Planning starts only when the user moves the project there. How the approved Product Definition (omniva-product-definition.html) will be built. Domain language lives in GLOSSARY.md; hard-to-reverse decisions live as ADRs in docs/adr/. This page is the readable index. Approved decisions and pending proposals are labelled separately.

Framing

How System Design is run

Approved
Approved · 24 Nov 2026 · Claude's recommendations accepted
  • Depth: the MVP is designed in detail; the long-term product (sharing, Vault, native mobile, AI) only as seams that nothing in the MVP blocks.
  • Where decisions live: GLOSSARY.md (domain language, no implementation detail), docs/adr/ (decisions that are hard to reverse, surprising and a real trade-off), and this page as the index. The handoff tracks overall progress.
  • Method: topics one at a time using the domain-modeling and grilling disciplines. wayfinder stays optional (user-invoked, needs an issue tracker).
  • Version control: F:\Omniva is a git repository; remote github.com/Mohaned178/Omniva.
  • Constraints (default until the user says otherwise): low running cost, a mainstream cloud host, EU-friendly data residency.
  • Builder and languages (answered in D7): mostly AI agents; TypeScript, NestJS.

D1

Domain model & glossary

Approved

The language every specification and line of code will use. Source of truth: GLOSSARY.md.

Approved · Round 1 · 24 Nov 2026 · Claude's recommendations accepted
#DecisionADR
1Record is the generic word for any entry; Item means only the possession block0001
2User signs in; Member is a user's participation in a workspace with a role; "Account" means only a financial account—
3Each member is a Person record in each workspace, connected to their User; "Me" is the same mechanism in the personal workspace—
4Records belong to their workspace; the creator is history, not ownership0002
5Block (10 fixed) → Type (decides the home module) → Template (preset with default dates and reminders)—
6An Event's start is also its key date, so reminders attach to key dates only—
7Projected money records (from obligations, never "paid") vs recorded; no "paid" state in the MVP0003
8Link (stored, named Relationship) vs Inferred connection (computed, never stored)—
9Identity documents have a Holder (a Person)—
10Plan Types have home modules (Trip → Travel; Move, Renovation → Home; generic Plan → Productivity)—
Approved · Round 2 · 24 Nov 2026 · Claude's recommendations accepted
  • Archived (universal) is separate from a block-specific lifecycle state: Item owned → disposed; Obligation active → ending → ended; Document valid → expired; Task open → done; Plan upcoming → in progress → past.
  • Archive keeps everything; delete is real deletion, shows links first, never cascades silently, and leaves only "a record was deleted" in the timeline (ADR 0004).
  • Recurrence: Obligations (cycle and next renewal), Tasks and Events only.
  • Currency: each Money record keeps its currency; each workspace has a main currency; converted totals are marked approximate and originals kept.
  • Key dates may be exact, month only (reminds safely early, invites confirming the day), or date missing.
  • Captures in the Inbox are not records: searchable, but no reminders, calendar entries or totals until sorted (ADR 0005).
D2

Architecture shape & boundaries

Approved
Approved · 24 Nov 2026 · Claude's recommendations accepted
  • Modular monolith plus a worker process on the same codebase (ADR 0006).
  • Internal modules by capability: Identity & Access · Workspaces & Membership · Records core · Life modules · Capture & Ingestion · Files · Scheduling & Reminders · Notifications & Digest · Automation · Insights & Inferred connections · Search · History · Portability. Modules use each other's interfaces only, never each other's data.
  • Life modules are type packs on Records core (ADR 0007).
  • Records are the source of truth; reminder schedules, search index, Insights and inferred connections are derived and rebuildable; the Activity Timeline is written in the same transaction as the change; changes reach derived parts through durable change notifications processed by the worker (ADR 0008).
D3

Tenancy, identity & access

Approved
Approved · Round 1 · 24 Nov 2026 · Claude's recommendations accepted
  • Isolation: one shared database, workspace enforced in two independent layers (application gate and database), mandatory cross-workspace tests (ADR 0009).
  • Permission checks from day one: every action checks membership and role, even in the personal-only MVP; module- and item-level access slot in later.
  • Sign-in: email and password, optional authenticator-app codes and passkeys; no social sign-in in the MVP; a proven authentication library or service, never custom security code.
  • Recovery: password reset by email link with notification; lost second factor via recovery codes, otherwise an email reset with a 72-hour waiting period, announced everywhere and cancellable.
  • Sessions: every device in the Security log, sign out one or all; re-authentication for full export, changing email, password or two-factor, and deleting the account.
  • Moving records (stage-2 seam): a chosen set moves as one all-or-nothing operation, keeps identity, recorded in both timelines, cross-workspace links shown first.
  • Staff access: none to user content by default; user-granted, time- and scope-limited support access in the Security log (ADR 0010).
Approved · Round 2 · 24 Nov 2026 · user decision

Public pages before sign-in (option A): visitors can see the home page, features, how it works, pricing, privacy and FAQ, with screenshots and short videos of the app, without an account. Using the app requires signing up or signing in. Rejected: an interactive demo with sample data (option B); guest mode storing real data without an account (option C, privacy risk).

D4

Data modelling

Approved
Approved · 24 Nov 2026 · Claude's recommendations accepted
  • Fields: anatomy and block structure in fixed columns; Type-specific and custom fields in a flexible structured field validated against the Type definition (ADR 0011).
  • Type definitions: built-in Types in code within their life-module pack, versioned with releases; custom types as workspace data; one definition shape (fields, key-date fields, default reminders, home module).
  • Key dates in one dedicated collection (record, kind, date, precision, missing), maintained by Records core; reminders, calendar and Overview read only from it.
  • Recurrence: iCalendar RRULE plus next occurrence; occurrences generated for a rolling window of about 13 months; date-only key dates have no time zone, timed Events keep theirs.
  • Money: integer minor units plus currency code; conversions record rate, date and source and are marked approximate.
  • Links: one collection (from, to, relationship, workspace); same-workspace rule enforced by the data; two-way by reading both directions.
  • History: a record's history is the Activity Timeline filtered to it (before/after); entries refer to records rather than copying content; content is purged on deletion.
  • Identifiers: random, non-guessable IDs everywhere, stable across workspace moves.
D5

Core platform services

Approved
Approved · 24 Nov 2026 · Claude's recommendations accepted
  • Reminders: derived schedule of due notices, checked every minute, idempotent sends, daily reconciliation with alerts (ADR 0012).
  • Delivery and digest: in-app and email via a transactional provider; bounces and failures tracked and shown; weekly digest in the user's time zone, respecting quiet hours; reminders stay in the Overview until handled.
  • Email forwarding: private random address per user, changeable; mail becomes a Capture with files and rule-based suggestions; accepted only from the user's verified sender addresses.
  • Files: separate encrypted file storage, short-lived download links, malware scanning, size limits per plan, image and PDF previews, originals kept.
  • Search: the database's built-in full-text search; indexes titles, types, tags, fields and linked records' titles; workspace-filtered; includes Captures.
  • Spreadsheet import: CSV or Excel → column matching to a Type → preview → one batch, undoable as a whole, one timeline entry.
  • Calendar feed: off by default with a plain-language note on what leaves Omniva; minimal titles by default, full titles optional; secret, revocable link.
  • Export: one ZIP with re-importable JSON, CSV per Type, original files and a README; prepared in the background; expiring link; re-authentication.
  • Automation and Insights: worker-run on change notifications; deterministic rules; automatic changes shown "by Omniva" and undoable.
D6

Security & privacy

Approved
Approved · 24 Nov 2026 · Claude's recommendations accepted
  • Encryption: in transit and at rest; plus per-workspace keys for files and designated sensitive fields, enabling crypto-shredding; not end-to-end and never described as such (ADR 0013).
  • Backups: daily encrypted, 14-day point-in-time recovery, same region, restores tested monthly.
  • Deletion: immediate from live systems; account key destroyed so files and sensitive fields are unreadable in backups at once; everything else gone within 14 days; stated plainly in the privacy policy.
  • Region and compliance: EU hosting; GDPR as the worldwide baseline; data-processing agreements and a public list of providers; no health data in the MVP.
  • Measurement: first-party, aggregate, no record content; no third-party trackers or ad pixels in the app; cookie-free analytics on the public website.
  • Logs: never contain user content; 30-day retention; error reports scrubbed.
  • Abuse protection: rate limits on sign-in, sign-up, reset and email intake; lockout with notification; upload limits.
  • Process: managed secrets store, never secrets in the (public) repository; dependency scanning; security review before beta; external penetration test before public launch.
  • Vault seam: storage and encryption behind an interface separating key holder from byte location.
D7

Technology stack & infrastructure

Approved
Approved · Round 1 · 24 Nov 2026
  • Builder: mostly AI coding agents, with the user reviewing.
  • Language preference: TypeScript; NestJS preferred by the user.
  • Budget (user): $0–1 per month. Conflicts with some approved reliability decisions; resolved in round 2.
  • Database: PostgreSQL only (ADR 0014).
  • Background jobs queued in PostgreSQL itself (ADR 0015).
  • Managed services over self-run servers, in the EU region.
  • No proprietary backend-as-a-service for core data or logic.
Approved · Round 2 · 24 Nov 2026
  • Budget: $0–1/month during development (local, plus free tiers for a staging copy with no real data); a small paid budget (roughly $30–60/month, to be confirmed by provider research) from the beta, when real users' data arrives.
  • Stack (ADR 0016): NestJS (API and worker) · Next.js / React (public pages and app) · one pnpm-workspaces repository (apps/web, apps/api, shared packages/) · Prisma (user's choice over Drizzle) · shared Zod schemas · pg-boss · Better Auth.
  • Prisma consequences: row-level isolation policies in hand-written SQL migrations; each request's transaction carries the workspace through a Prisma client extension; full-text search through raw SQL.
Approved · Round 3 · 24 Nov 2026 · Claude's recommendations accepted
  • Development: local Docker (PostgreSQL, MinIO, Mailpit); staging on free tiers with no real data. $0.
  • Beta providers (ADR 0017): Neon PostgreSQL, Frankfurt, 14-day history · Render, Frankfurt (web, API, worker) · Cloudflare R2, EU jurisdiction · Mailgun EU for sending and receiving (Lettermint fallback) · AWS KMS, Frankfurt, one master key plus per-workspace data keys · ClamAV in the worker · Sentry EU and a free uptime monitor alerting on outages and failed reminder reconciliation.
  • Estimated beta cost: about $55–80/month plus a domain; prices to be confirmed at account setup.
Approved · Round 4 · 24 Nov 2026 · user decision: use Redis
  • Redis (or compatible Valkey) for shared rate limiting, a secondary store for session lookups (PostgreSQL stays the source of truth) and a short-lived cache of non-personal data (ADR 0020).
  • Jobs stay in PostgreSQL: reminder schedule, change notifications and all background jobs remain on pg-boss.
  • Rules: no record content in Redis; every key expires; encrypted connections; EU only; Redis is disposable and the app keeps working without it.
  • Local: Redis in Docker. Provider: pending confirmation (see below).
D8

Reliability & testing

Approved
Approved · 24 Nov 2026 · Claude's recommendations accepted
  • Test layers: test-first unit tests for domain rules; integration tests on a real PostgreSQL in Docker (never a mocked database); Playwright end-to-end tests for the 7 essential journeys and the light trip.
  • Isolation suite blocks every build: cross-workspace calls on every endpoint, a database-level bypass test, and no endpoint without an isolation test (ADR 0018).
  • Reminder correctness: controllable clock; daylight saving, month-only dates, leap years, time-zone moves, end-of-month recurrence, auto-roll vs expiry, quiet hours; property-based "sent exactly once" tests; reconciliation tested by corrupting the schedule.
  • CI: GitHub Actions on every pull request (lint, types, unit, integration, isolation, end-to-end); red blocks merging; protected main; auto-deploy to staging; manual promote to production.
  • Environments: local, staging (synthetic data only), production; real user data only in production.
  • Production watching: reminder metrics (due, sent, failed, delayed); alerts on more than 5 minutes' delay, reconciliation differences, delivery-failure spikes; health checks; content-free logs.
  • Migrations: forward-only, expand–contract, run before new code, rehearsed on staging, including hand-written isolation policies.
  • Incidents: missed reminders and isolation failures logged as incidents, affected users told honestly, short write-up with cause and fix.
  • Monthly restore drill: automated restore into a temporary Neon branch, counts and reminder sample checked, alert on failure.
D9

API & clients

Approved
Approved · 24 Nov 2026 · Claude's recommendations accepted
  • API: REST with an OpenAPI description generated by NestJS; a typed client generated for web (and mobile later); inputs defined by the shared Zod schemas. Rejected: GraphQL, tRPC.
  • Versioning: /v1/…; additive changes only within a version; older mobile versions supported for a set period.
  • The Next.js server never touches user data: public pages pre-rendered, app pages in the browser using the API only (ADR 0019).
  • Sessions: Better Auth in secure HTTP-only cookies on subdomains of one domain, CSRF protection; tokens for mobile later.
  • Front end: TanStack Query, React Hook Form with shared Zod schemas, shadcn/ui on Radix with Tailwind.
  • Arabic-ready: all strings in translation files (next-intl), direction-neutral styling, locale formatting for dates, numbers and currencies.
  • Mobile web: fully responsive, camera capture in the browser, add to home screen, no offline mode in the MVP.
  • Accessibility: WCAG 2.2 AA, checked automatically with axe in the end-to-end tests.
